GOAL
================================================================
Create a production-grade, portable multi-agent configuration that:

1.  Uses OpenCode as the runtime environment
2.  Supports 5 separate DeepSeek API keys (independent accounts)
3.  Includes a dedicated "Task Planner" (architect) agent that
    decomposes goals into a task DAG
4.  Includes parallel "Builder" agents that execute independent
    tasks concurrently
5.  Includes a "Reviewer" agent that validates completed work
6.  Includes a "Browser Agent" capable of navigating real websites
    via accessibility snapshots
7.  Uses AACP (Agent Action Compression Protocol) for ALL
    inter-agent coordination messages to cut token cost
8.  Uses A2A (Agent-to-Agent) protocol for remote / browser agent
    communication and capability discovery
9.  Uses ACCP (Agent Context Compression Protocol) for context
    state handoff between agents
10. Can be dropped into ANY new project directory and work
    immediately
11. Handles API key rotation and 429 rate-limit failover
    automatically

================================================================
ARCHITECTURE OVERVIEW
================================================================

LAYER 1 — Runtime
  OpenCode CLI as agent runtime and configuration layer

LAYER 2 — Models
  DeepSeek V4-Flash for high-concurrency parallel workers
    (2500 concurrency limit per account)
  DeepSeek V4-Pro for planner / architect / reviewer roles
    (stronger reasoning)

LAYER 3 — Coordination Protocol (NEW)
  AACP  = compressed coordination packets (task routing,
          resource refs, action verbs, metadata)
  ACCP  = compressed context state between agent handoffs
  A2A   = remote agent discovery + HTTP/JSON-RPC transport

LAYER 4 — Tools
  Browser MCP for web automation (opencode-browser-control)

LAYER 5 — Resilience
  5-account key pooling + 429 failover + cooldown tracking

STEP 3 — AACP PROTOCOL LAYER (NEW)
================================================================
AACP = Agent Action Compression Protocol.
Purpose: Replace verbose natural-language coordination between
agents with compact semantic packets.

Create ~/.config/opencode/protocols/aacp.md with the spec:

PACKET FORMAT (JSON, one line per message):
{
  "v": 1,
  "op": "DISPATCH|RESULT|QUERY|ACK|FAIL",
  "task": "t1",
  "role": "builder|browser|reviewer",
  "dom": "code|web|fs|test",
  "ref": ["src/feature/**", "https://x.com"],
  "ret": ["files", "stdout", "snapshot"],
  "meta": { "pri": 1, "ttl": 60, "hash": "..." }
}

RULES:
- NEVER send full task descriptions between agents
- Task body lives in the DAG; agents exchange only task IDs
- Reference resources by URI, not by inlined content
- Use short verbs: DISPATCH, RESULT, QUERY, ACK, FAIL
- Cache identical packets by hash -> zero re-tokenization
- Coordination overhead should drop ~30% on multi-hop flows

ENCODER:
Create ~/.config/opencode/protocols/aacp-encoder.js exporting:
  encode(taskId, op, payload) -> compact JSON string
  decode(packetString)        -> structured object

================================================================
STEP 4 — ACCP PROTOCOL LAYER (NEW)
================================================================
ACCP = Agent Context Compression Protocol.
Purpose: Compress context state during agent handoffs so the
receiving agent doesn't re-read the whole transcript.

Create ~/.config/opencode/protocols/accp.md with the spec:

CONTEXT SNAPSHOT FORMAT:
{
  "v": 1,
  "run_id": "...",
  "cursor": "t5",
  "facts": [
    { "k": "files_created", "v": ["src/a.js"] },
    { "k": "tests_passing", "v": true },
    { "k": "blockers", "v": [] }
  ],
  "intent": "code_gen | refactor | test | research",
  "delta": [ "only what changed since last snapshot" ]
}

RULES:
- Each agent handoff passes an ACCP snapshot, not full history
- "facts" holds durable state; "delta" holds last-step changes
- Snapshots are content-addressed; identical snapshot = cache hit
- Reviewer accepts snapshots, not transcripts

================================================================
STEP 5 — A2A PROTOCOL LAYER (NEW)
================================================================
A2A = Agent-to-Agent protocol (JSON-RPC 2.0 over HTTP/SSE).

Create ~/.config/opencode/protocols/a2a.md with the spec:

AGENT CARD (served at /.well-known/agent.json):
{
  "did": "did:local:browser-agent",
  "name": "browser-agent",
  "capabilities": [
    "web_navigate", "form_fill", "data_extract", "screenshot"
  ],
  "endpoints": {
    "rpc": "http://localhost:8789/rpc",
    "stream": "http://localhost:8789/stream"
  },
  "limits": { "max_rps": 5, "timeout_ms": 60000 },
  "trust": 0.95
}

RULES:
- Every remote agent (browser, external tools) exposes a Card
- Planner queries the A2A registry for capability discovery
- Calls use JSON-RPC methods: task.dispatch, task.status,
  task.cancel, task.result
- Streaming via SSE for long browser tasks
- Messages are signed with a local DID for non-repudiation

STEP 6 — DEFINE AGENT ROLES
================================================================
Create agent files in ~/.config/opencode/agents/

--- AGENT 1: planner (primary) ---
File: planner.md
Model: deepseek-account-1/deepseek-v4-pro
Mode: primary
Role: Decompose goals into task DAG; never execute tasks
Protocols:
  - Emits AACP packets to builders
  - Queries A2A registry for capability match
  - Receives ACCP snapshots from reviewers
Permission: read all, no edit, no bash
System prompt:
"You are a senior engineering planner. Decompose goals into
parallelizable task graphs. Emit AACP packets only — never
inline task bodies. Query the A2A registry before assigning
remote tasks. Output strict JSON matching task-dag schema."

--- AGENT 2-4: builder-1 .. builder-3 (subagents) ---
Files: builder-1.md, builder-2.md, builder-3.md
Models:
  builder-1 -> deepseek-account-2/deepseek-v4-flash
  builder-2 -> deepseek-account-3/deepseek-v4-flash
  builder-3 -> deepseek-account-4/deepseek-v4-flash
Mode: subagent
Role: Execute exactly one atomic task; report via AACP RESULT
Protocols:
  - Decodes AACP DISPATCH packets
  - Emits AACP RESULT + ACCP snapshot on completion
Permission: full file read/write, bash allow, browser deny
System prompt:
"You are a focused builder. Complete exactly one task.
Parse incoming AACP DISPATCH. On finish, emit AACP RESULT with
evidence URIs and an ACCP snapshot. Do not narrate."

--- AGENT 5: browser (subagent, A2A server) ---
File: browser.md
Model: deepseek-account-5/deepseek-v4-flash
Mode: subagent
Role: Web navigation, form filling, data extraction
Protocols:
  - Registers Agent Card at localhost:8789
  - Accepts A2A task.dispatch from planner
  - Uses browser_snapshot to get numbered refs (e1, e2)
Permission: browser allow, fs write limited, bash deny
System prompt:
"You are a browser operator. Use browser_snapshot to see the
page. Use browser_click and browser_type by ref. Never guess
CSS selectors. If a ref is stale, take a new snapshot. Reply
to A2A calls only with AACP RESULT packets."

--- AGENT 6: reviewer (subagent) ---
File: reviewer.md
Model: deepseek-account-1/deepseek-v4-pro
Mode: subagent
Role: Validate work against the DAG evidence rules
Protocols:
  - Consumes ACCP snapshots, not transcripts
  - Emits AACP ACK or FAIL
Permission: read all, bash limited to test/lint
System prompt:
"You are a strict reviewer. Accept an ACCP snapshot, check
facts and delta against the task brief. Emit AACP ACK on pass,
AACP FAIL with reasons on reject. Never request transcripts."

--- AGENT 7: integrator (primary) ---
File: integrator.md
Model: deepseek-account-1/deepseek-v4-pro
Mode: primary
Role: Merge parallel outputs, resolve conflicts
Protocols:
  - Aggregates ACCP snapshots from all builders
  - Emits final report
Permission: full access
System prompt:
"You are the integrator. Collect ACCP snapshots. Resolve
conflicts. Produce final artifact. Report what was merged,
what conflicted, what was dropped."

STEP 7 — TASK DAG SCHEMA
================================================================
Create ~/.config/opencode/context/task-dag.md

{
  "run_id": "string",
  "objective": "string",
  "tasks": [
    {
      "id": "t1",
      "subject": "string",
      "description": "string",
      "role": "builder|browser|reviewer",
      "model": "provider/model (optional override)",
      "blockedBy": ["t0"],
      "reviewBy": "reviewer",
      "evidence": {
        "files": ["path/to/output"],
        "commands": ["command that must pass"]
      },
      "writes": ["src/feature/**"]
    }
  ]
}

Only task IDs travel between agents (via AACP).
Only task bodies stay in the DAG file.

KEY TECHNICAL NOTES
================================================================
- DeepSeek's 2500 concurrency limit is per-ACCOUNT, not per-key.
  Five independent accounts = theoretical 12,500 concurrency.

- V4-Flash is ~5-6x cheaper than V4-Pro for output tokens.
  Use Flash for parallel builders, Pro for planner/reviewer.

- AACP replaces verbose coordination text with compact packets.
  Real-world benchmarks show 7-34% token reduction on 4-hop
  flows (higher savings on more complex coordination).

- ACCP passes facts + delta instead of full transcripts,
  keeping reviewer context bounded.

- A2A registry enables capability-based routing. Planner picks
  agents by capability match, not hard-coded IDs.

- Browser agent needs accessibility refs, not CSS selectors.
  Numbered refs (e1, e2) from ARIA snapshots fail loudly
  when stale — no silent selector drift.

- DeepSeek V4-Flash is text-only; DOM snapshots as text means
  no vision tokens burned on screenshots.

- A2A and AACP messages are NOT visible in the OpenCode TUI.
  Side-channel logging is mandatory.

- Key rotation caveat: OpenCode's native multi-provider config
  does NOT auto-rotate on 429. Pin each builder to a different
  provider, or use key-rotator.js as a custom tool.

- Q-KVComm (KV cache compression) is out of scope for v2.0 —
  DeepSeek public API does not expose KV cache exchange yet.
  Revisit when provider support lands.
